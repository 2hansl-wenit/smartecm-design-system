- 문서 HTML의 Pretendard 표기는 폰트 설치를 의미하지 않는다. 다음의 **공식 Pretendard Variable 1.3.9 동적 서브셋 CSS**를 문서 `<head>`에서 반드시 불러온다: `https://cdn.jsdelivr.net/gh/orioncactus/pretendard@v1.3.9/dist/web/variable/pretendardvariable-dynamic-subset.min.css`.
- 폰트 스택은 `"Pretendard Variable", Pretendard, "Noto Sans KR", "Apple SD Gothic Neo", "Malgun Gothic", sans-serif`를 사용한다. 생성된 단일 HTML 결과물도 같은 링크를 포함한다.
- 온라인 PC에서는 CDN에서 폰트를 불러와 설치 여부와 상관없이 같은 서체를 사용한다. **폐쇄망/오프라인 PC에서는 웹 CDN에 접근할 수 없으므로** 고객사에 맞는 로컬 WOFF2 자체 호스팅 방식을 별도 준비한다. 폰트 파일을 동봉할 경우 SIL OFL 조건과 저작권 문구를 준수한다.
- PDF 인쇄 전에 폰트 로딩 상태를 확인하고 글자 폭·문단 줄바꿈 변화를 검수한다. 생성된 PDF는 폰트 포함 여부를 확인한다. CDN 장애나 차단 시에는 폴백을 허용하되 동일한 화면이라고 보장하지 않는다.
- 폰트 미설치 PC에서도 표시되도록 만든 웹폰트 로딩은 **출력 형식 미지정 시 HTML 기본 제작** 규칙과 함께 적용한다. PDF/DOCX 사용자가 명시한 형식이 우선이다.

# 최우선 기준 — 제목 위계, 문장별 표 너비, HTML 기본 전달 (2026-10-28)

- **1레벨 제목 21pt, 번호 17pt**. 섹션 번호(예: 03)는 전용 42px 칸, 제목은 오른쪽 내용 칸에 배치한다. 기존 13pt에서 충분히 크기를 키워 하위 항목과 위계를 명확히 한다.

- **표 열 너비는 내용의 길이와 성격을 분석**해 정한다. 긴 기능명에는 첫 열을 넓게 지정한다. 예시: 기능 36%, 설명 38%, 증적 26%. 모든 표에 같은 비율을 강제하지 않는다. `table.columnWidths`를 쓰면 헤더 수만큼 퍼센트 배열을 지정하고 합계를 100으로 맞춘다. 표를 A4로 인쇄해 불필요한 줄바꿈을 확인한다.
- **문서 결과물 형식이 지정되지 않으면 단일 HTML 파일(.html)이 기본이다.** 같은 자료를 PDF/DOCX로 중복 작성하지 않는다. 파일 상단에 화면에서 항상 보이는 **PDF로 인쇄** 버튼을 제공하고, 클릭하면 `window.print()`를 실행하게 한다. 인쇄 CSS에서는 화면용 툴바를 숨긴다. 사용자가 PDF·DOCX 등 다른 출력 형식을 명시했다면 그 요청이 우선이다.
- 제작 시작점은 `templates/printable-document.html`이며, A4 20/21/19mm 여백, 본문 자동 흐름, 인쇄 시 글자·표 잘림 방지와 기본 푸터 없음 규칙을 유지한다. 다운로드 파일 생성이 불가능한 환경이라면 완전한 실행형 HTML 코드를 제공한다.
- 작성하는 문서의 내용은 사용자가 제공한 자료에 근거해야 하며, 예시 데이터가 실제 고객 검증 결과로 혼동되지 않게 한다. 인쇄 버튼은 PDF 파일이 자동으로 생성됐다는 의미가 아니다.

# 최신 기준 — 웹/PDF 타임라인 표현 일치 (2026-10-28)

- 문서의 4단계 일정 타임라인은 화면과 PDF 모두 **하나의 연결선 + 4개 원형 노드** 형태를 유지한다. 인쇄 시 배경 그래픽이 비활성화되어 선이 사라지는 것을 방지하도록 `@media print`에서 연결선을 배경색 대신 **실제 border-top**으로 그린다.
- 원형 노드는 PDF에서 배경색과 box-shadow에만 의존하지 않는다. 명시적 테두리와 `print-color-adjust: exact`를 사용하고, 4열 배치와 단계 제목/설명 정렬을 보존한다.
- 일정2(주차 격자 및 기간 막대)는 기존 `print-color-adjust: exact`가 적용되어 있음을 확인했다. 격자, 기간 구간, 표의 헤더 및 행 구분이 인쇄에서도 유지되는지 최종 PDF에서 확인한다.

# 과거 기록 — 인쇄 고정 푸터 (현행 정책으로 폐기) 및 핵심 질문 (2026-10-28)

- PDF 인쇄 시 모든 페이지 하단 여백의 같은 위치에 문서명(좌측)과 자동 페이지 번호(우측)를 고정한다. HTML 본문 끝의 푸터는 인쇄에서 숨긴다.

- 핵심 검토 질문은 초기 디자인의 얇은 위·아래 가로선으로 복원한다. 앞에 크게 분리한 여는 따옴표(“), 오른쪽에 질문 문장만 놓는다. 별도 레이블과 타깃 아이콘은 사용하지 않는다.
- styles/doc-layout.css를 styles/document.css 다음에 로드해야 한다. 다른 현황표, 데이터 표, 확인 질문 묶음 및 산출물 스타일은 그대로 유지한다.

# 확인 질문 영역 최신 디자인 확정 후보 (2026-10-28)

스토리지 검증 예시의 확인 질문은 **아주 연한 쿨그레이 배경(#F7F8FB)의 한 덩어리**로 묶는다. 큰 카드 테두리·그림자·둥근 모서리를 사용하지 않는다. 작은 체크리스트 선형 아이콘은 왼쪽 상단에 두고 **'확인 질문' 제목과 상단 정렬**한다. 오른쪽의 제목 및 4개 문항은 2열/2행의 단정한 그리드로 배치하되 간격을 과하게 벌리지 않는다. 모바일에서는 질문을 한 열로 표시한다.

**기존 산출물 안내는 왼쪽 얇은 강조선으로 표현하는 이전 스타일을 유지**한다. 이 배치는 시각적 검토 중인 후보안이다. 아래 이전 디자인 기록보다 이 최신 지침을 우선한다.

## 기술 검증 확인 질문의 레이아웃 · 최신 수정

- 검증 목적 본문 뒤의 **'확인 질문' 제목과 질문 4개를 한 덩어리로 오른쪽 칼럼에 배치**한다.
- 왼쪽 칼럼은 넓은 여백으로 남기고 위쪽에만 작은 선형 체크리스트 아이콘 하나를 배치한다. 아이콘을 글자마다 반복하거나 바탕색 카드로 감싸지 않는다.
- 오른쪽 질문은 기존처럼 간결한 대시(—) 표시와 2열 × 2행을 유지한다. 좁은 화면에서는 1열로 전환한다.
- 아래 **산출물은 이전의 간단한 왼쪽 강조선 스타일로 복원**한다. 산출물에 원형 정보 아이콘을 붙이지 않는다.
- 이 패턴은 기술 검증 섹션의 확인 질문에만 적용하며, 다른 표나 일반 문서 스타일은 수정하지 않는다.

# 최신 문서 구성 원칙 (2026-10-28)

문서 유형은 **1. 결과보고서 / 2. 수행계획서 / 3. 제안서**로 통일한다. 기술 검증, 장애 조치 등의 세부 사항은 본문 제목에 표현한다.

2페이지 이상 문서의 큰 제목과 도입문은 **1페이지에서 단 한 번만** 작성한다. 이후 페이지는 앞선 문단, 표, 섹션에서 자연스럽게 이어지며, 페이지마다 표지나 대제목을 반복하지 않는다. 고정된 2페이지 분할과 본문 잘림을 금지하고, 실제 출력 결과로 페이지 나눔을 검증한다.

강조 정보(핵심 질문·주의·산출물)는 큰 테두리 박스 대신 **왼쪽 선형 아이콘 1개 + 오른쪽 텍스트**의 2단 구성과 충분한 여백으로 독립시킨다. 미리보기 구현은 `styles/doc-layout.css`를 따른다.

이 최신 지침이 아래의 과거 분류 및 페이지 분할 관련 지침보다 우선한다.

# Agent Document System · 문서 디자인 기준 (v0.1 Draft)

## 목적

기존 Agent UI System과 동일한 시각 원칙을 사용하는 A4 비즈니스 문서. 대상은 결과 보고서, 운영 현황 및 조치 계획서, 기술 검증 계획서, 간단한 제안서이다.

사용자가 첨부한 3개 PDF의 **내용 구성만** 참고했다.
- 장애 결과 보고서: 개요 → 현황 → 원인 → 조치 → 재발 방지.
- 운영환경 현황 및 개선 계획서: 추진 배경 → 핵심 지표 → 대상 현황 → 작업 단계 → 일정.
- HCI 전환 기술 검증 계획: 목적 → 질문 → 검증 항목 / 방법 → 산출물 → 판정 기준.

원본 PDF의 시각적 장식과 고객 정보, 도메인, 계약 금액을 복제하지 않는다. 공개 미리보기는 비식별화된 가상·축약 문구를 사용한다.

## 핵심 디자인 원칙

1. **A4 인쇄를 우선**한다. 여백: 상단 20mm, 하단 17mm, 좌우 21mm를 초안으로 사용한다.
2. 큰 제목(27pt)과 절제된 작은 메타데이터, 명확한 01/02/03 섹션 제목(13pt)을 기본 계층으로 한다.
3. 본문 약 10pt, 표 약 9.2pt, 적절한 행간(1.72). 강제로 한 페이지에 맞추기 위해 무리하게 축소하지 않는다.
4. Pretendard 우선 사용, 합법적인 시스템 폰트로 대체 가능. 사용자가 제공하지 않은 폰트 파일을 임의로 첨부하지 않는다.
5. Letter-spacing은 0. 진한 본문과 중간 명도의 설명 글씨, 충분한 섹션 간격을 사용한다.
6. **박스와 배경면으로 모든 콘텐츠를 가두지 않는다.** 구분은 공백·타이포그래피·1px 구분선으로 표현한다.
7. 표는 상단 강조선과 가는 행 구분선, 왼쪽 정렬, 최소 색상으로 구성한다. 박스형 셀·과도한 줄무늬 배경을 피한다.
8. 핵심 숫자는 한 줄의 타이포그래피 스트립으로 사용하고, 필수 결재·주의 내용만 가는 왼쪽 강조선으로 처리한다.
9. 포인트 컬러는 섹션 번호와 정말 필요한 강조에 소량 사용한다. 기본은 흑백·회색 계층이다.
10. 화면 컴포넌트 기준의 기본 모서리는 5px이고, 문서는 모서리 없는 열린 구성이 원칙이다. 불필요한 pill·badge·카드를 문서에 남용하지 않는다.
11. 로고, 헤더, 푸터, 작성자·보고일 등은 필요한 정보만 표기한다. 임의 회사명·고객명·승인자를 만들어내지 않는다.

## 문서 구성 패턴

### 1. 결과 보고서

제목·보고일 → 짧은 개요 → 사실 기반 현황 → 발생 원인 및 경과 → 조치 결과 → 재발 방지·후속 계획.

'추정'과 '확인'을 구분한다. 문제 발생·복구 시각, 영향 범위와 상태는 주어진 증적에서만 작성한다. 완료되지 않은 조치를 완료로 표시하지 않는다.

### 2. 현황·개선 계획서

제목·기준일 → 추진 배경 → 주요 수치(필요한 경우) → 전체 관리 현황 표 → 조치 대상·예외 → 추진 단계 → 일정과 역할·위험 → 필요한 결정사항.

전체 사이트 수와 전환 대상 수, 예외·비용·부가세 여부를 구분한다. 불확실한 일정은 확정 일정으로 표시하지 않는다.

### 3. 기술 검증 계획서 및 간단 제안서

목표·의사결정 질문 → 검증 범위와 가정 → 목적 / 주요 확인 질문 / 검증 방법 / 증적 / 예상 산출물 패턴 반복 → 비교·매핑표 → 제한사항 → 완료 조건 및 최종 산출물.

계획/예정/미검증 상태와 실제 검증 완료 상태를 혼동하지 않는다. 기술 검증 계획서가 길다면 섹션을 확장하고 페이지를 나누되, 반복되는 패턴을 유지한다. 제안서는 고객의 목적·선택 기준을 먼저 제시한다.

## 생성·검수 지침

- 사용자가 원한 최종 형식(Word, PDF, HTML)을 명확하게 준수한다. HTML 미리보기는 DOCX/PDF의 대체물이 아니다.
- 긴 보고서·서식은 DOCX로 작성 후 PDF로 변환하는 방식을 우선 고려한다. 인쇄/PDF 페이지 수와 편집 가능 여부를 명시한다.
- 본문 텍스트와 표의 사실, 날짜, 단위, 인용·출처를 원본과 대조한다.
- 각 페이지를 실제로 렌더링하여 한글 깨짐, 표 잘림, 텍스트 겹침, 고아 제목, 과도한 공백, 빈 끝 페이지를 확인한다.
- 인쇄된 A4에서 헤더·푸터 및 페이지 번호가 맞는지 확인한다.
- 사용자가 제공한 문서 내용은 작업 근거로만 사용하고, 비공개 데이터는 공개 디자인 미리보기에 삽입하지 않는다.

## 시안 수정 · 2026-10-28 (사용자 피드백)

- **문서 최상단 장식 헤더/발행자명/문서 유형·날짜 영역은 모든 샘플에서 제거한다.** 문서 시작은 제목 블록으로 하며, 실제 문서에 필수인 날짜나 결재 정보는 명시적 요구가 있을 때 제목 아래의 간결한 메타데이터로 배치할 수 있다. 최상단 장식용 헤더를 복원하지 않는다.
- 섹션 번호(01, 02...)는 섹션 제목과 **동일한 13pt**를 기본으로 하고 기준선 정렬 및 **7px 간격**으로 밀착시킨다.
- KPI 숫자 및 같은 위계의 일정값(예: 08, 06, 11월)은 **모두 23pt 동일 크기**를 적용한다. 단위는 본문보다 작은 크기로 분리할 수 있다.
- 데이터 표: **표 최상단은 얇은 1px 중립선**, **thead 하단은 굵은 2px 본문색 선**, tbody 행 구분은 얇은 선으로 한다. 열 간에는 1px 옅은 세로 구분선을 추가하고, 외곽 상자 테두리는 만들지 않는다. 사실 요약(dt/dd)에도 레이블·값 사이 가는 세로 구분선을 사용한다.
- 단계별 추진 일정은 텍스트 화살표 나열 대신 **가로 막대 + 원형 노드 4개 + 아래 단계명**으로 도식화한다. 간결한 보조 설명을 넣되 실제 일정/진행률은 임의로 만들지 않는다.
- 이 값들은 문서 전용 규칙이며 웹 콘솔 UI 전체의 동작과는 별개다. A4 인쇄 결과에서 여백·줄바꿈·선명도를 재검토한다.

## 현황표·일반 표 위계 수정 · 2026-10-28

- **현황표(dt/dd 형태)**: 왼쪽 레이블은 부드러운 쿨그레이 배경(#F6F7F9)과 짙은 회색 글씨(#667383), 600 weight로 구분한다. 오른쪽 데이터는 주 텍스트색과 610 weight를 사용한다. 레이블/값 사이에는 **끊기지 않는 1px 세로 구분선**을 둔다. 외곽 테두리나 카드 배경은 금지한다.
- **일반 데이터 표(table/thead/tbody)**: 테이블 맨 위의 선은 **0.75pt(약 1px)** 중립색, 헤더 아래 구분선은 기존 2px보다 얇은 **1pt 슬레이트색**으로 통일한다.
- thead 행에는 **컬럼 사이 세로선이 없어야 한다**. 헤더 텍스트는 #667383, 650 weight로 구성한다.
- tbody는 가는 행 구분선과 가는 0.75pt 열 구분선으로 내용의 각 열을 구분한다. 셀 배경색과 외곽 테두리는 사용하지 않는다.
- 이 두 표 스타일을 구별하여 적용한다. 특히 현황표의 왼쪽 레이블 영역을 HTML의 thead로 잘못 취급하지 않는다.
- 실제 A4 인쇄 시 행 줄바꿈과 배경 인쇄 옵션을 확인한다.

## 2026-10-28 · 현황표 원래 스타일 복원 (최신 지침)

사용자 요청에 따라 `발생 현황` 등의 왼쪽 항목명 / 오른쪽 값 표(`.fact`, `.fact dt`, `.fact dd`)를 **2026-10-28 초기 개정 스타일로 정확히 복구**한다.

- 왼쪽 항목에 배경색을 넣지 않는다. 페이지와 동일한 흰 배경을 유지한다.
- 항목명은 일반 회색 본문(`var(--muted)`), 9.3pt, 굵게 처리하지 않는다.
- 오른쪽 값은 9.8pt, font-weight 580.
- 두 열은 124px / 나머지 영역과 12px 간격. 항목명 우측에 짧은 1px 세로 구분선을 남긴다.
- 행은 상하 10px 여백과 가는 가로선을 사용한다. 연속 배경면, 전체 높이 구분선, 그레이 레이블 영역은 사용하지 않는다.
- 일반 데이터 테이블의 최근 변경(상단 0.75pt, 헤더 아래 1pt, thead 세로선 없음)은 **별도로 유지**한다.

위 지침은 직전의 '회색 레이블 배경/연속 구분선' 규칙을 명시적으로 대체한다.
